# Skill catalogue

This guide lists the explicit workflows and implicit stack standards, explains how to invoke and update them, and follows a typical planning and delivery run. Maintainers use [skill guidelines](skill-guidelines.md) to change the collection.

## Use

Discuss a change with your coding agent, then invoke a skill by name, followed by any text it should take into account:

```text
/jg-plan
```

In Codex, type `$jg-plan` instead.

The collection has two kinds of skill. Explicit skills run only when you invoke them by name: each sets `disable-model-invocation: true` in its frontmatter and ships an `agents/openai.yaml` policy that disables implicit invocation. Explicit-only loading is verified with Claude Code and Codex.

Implicit skills load on their own when a task touches their stack, such as a migration for `jg-postgres` or a component for `jg-react`. They omit that flag, and their `agents/openai.yaml` allows implicit invocation. You can still invoke one by name to load it before a task. Implicit loading is verified with Claude Code and Codex.

## Update and remove

Run these from your repository's root:

```bash
npx skills update -p jg-brainstorm jg-plan jg-challenge-plan jg-challenge-session jg-breakdown jg-execute jg-debug jg-debug-session jg-pause jg-command jg-review jg-push jg-deliver jg-review-session jg-feedback jg-session jg-frontend jg-react jg-pwa jg-seo jg-svg jg-graphics jg-nestjs jg-postgres jg-redis jg-node jg-packages jg-npm-package jg-monorepo jg-bash jg-docker jg-ci jg-zod jg-testing
```

```bash
npx skills remove jg-brainstorm jg-plan jg-challenge-plan jg-challenge-session jg-breakdown jg-execute jg-debug jg-debug-session jg-pause jg-command jg-review jg-push jg-deliver jg-review-session jg-feedback jg-session jg-frontend jg-react jg-pwa jg-seo jg-svg jg-graphics jg-nestjs jg-postgres jg-redis jg-node jg-packages jg-npm-package jg-monorepo jg-bash jg-docker jg-ci jg-zod jg-testing
```

Both commands name the skills, so other skills in the project are left alone. Update refreshes only the skills you already have, so rerun the install command to add skills released since you installed.

## Skills

### Explicit skills

| ---------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jg-brainstorm`        | Thinks an idea through with you and recommends a direction before planning.                               | Nothing.                                                                                                                                              |

| `jg-deliver`           | Delivers completed work to its defined stops and verifies whether it is safe to close.                    | Task-scoped commits, pushes, integration, publication, deployment, cleanup and guarded delivery state, through repository procedures.                 |

| `jg-feedback`          | Assesses feedback independently and recommends what to adopt, reject, or adjust.                          | Nothing.                                                                                                                                              |
| `jg-session`           | Finds named Codex or Claude Code sessions and answers questions about them.                               | Nothing.                                                                                                                                              |

Each implicit skill states the versions it was written for and, for anything without an installed version, such as a hosted service or browser behavior, the month it was last reviewed. Items that need a newer version are marked with it, and apply only when that version or a later one is installed. When an installed version is newer than the one a skill was written for, or a review month is more than six months old, the agent checks the skill's version-specific items against the official guidance before relying on them and follows that guidance where an item differs. Skills don't list everything: where a skill says nothing, the agent follows the installed version's official guidance and may use its newer features in new code, after confirming them in the official documentation. When that documentation can't be reached, the agent keeps the skill's approach and says so. It reports any item that looks outdated and offers to open an issue here.

## Planning runtime

Persisted planning workflows require Node.js 24.15+ and project-local jg-plans 0.6.1 or newer with CLI schema 3:

```sh
npm install --save-dev --save-exact jg-plans@0.6.1
./node_modules/.bin/jg-plans --version --json
```

The eight planning reader/writer skills use this one native contract. Use the project's existing manager and installed CLI, or its documented built entry when developing jg-plans. This repository keeps tooling in `website/`: run `npm ci` there and use `website/node_modules/.bin/jg-plans` from the root. Runtime consumers retain their production dependency. Skills never install automatically or use global executables. No-plan tasks, code-only reviews, brainstorming and pause need no planning CLI.

New plans use `jg-plans/<timestamp>_<slug>/`. They record priority, affected repositories, a required delivery map from each repository to its defined stop, and any new error codes. Each repository's `docs/delivery.md` defines ordered stops, a default, operators, procedures and preconditions. Approving the plan covers the selected agent-operated delivery steps, including publication and deployment. A developer-operated step remains the developer's; later verification confirms it before delivery is complete.

Plan statuses are pending, in progress, done and delivered. Done means implementation is complete; delivered means the defined delivery was verified. Pending, in progress and done plans remain active and reserve error codes until delivered. jg-plan checks overlapping claims in the affected planning roots.

Breakdown binds milestones to the plan id/revision and a structural fingerprint excluding created_at, updated_at, revision, status, priority and delivery. Reprioritization or delivery-only retargeting preserves implementation and bindings. Changed body or contractual metadata needs coverage reassessment. An explicit retarget of a delivered plan records the new map and status done together before delivery effects. A missing expected sequence never means completion. Generic checks and bindings grant no authority.

jg-deliver owns the live closing report: branch/HEAD, committed and pushed source, required merges, deployed revision or published version, resource cleanup and Safe to close. It sets delivered only after verified completion. jg-execute reads neighboring jg-review, jg-push and jg-deliver instructions; supervised execution uses the same report without publication effects.

## A typical run

1. `jg-brainstorm` thinks the idea through with you and ends with a summary that recommends the next step: `jg-plan`, or `jg-execute` for a small, settled change.
2. `jg-plan` asks about any decision that is yours to make, then turns the discussion into a plan under `jg-plans/` and asks for approval. When the idea isn't clear enough to plan, it points you back to `jg-brainstorm`.
3. Optionally, `jg-challenge-plan` returns a verdict, any required corrections, and numbered decisions, and `jg-plan` with your answers revises the same plan. For an independent challenge, run `jg-challenge-session` with the planning session's name from a separate session or another coding agent. If feedback remains, paste the complete report from its copyable code block into the planning session with `jg-feedback`; a clean result says `Nothing to forward.`
4. Optionally, `jg-breakdown` writes `milestones.md` when the plan has real milestone boundaries, with tool-assigned UUIDs, explicit status markers, and a binding to the current plan id, revision, and content fingerprint. It preserves matching completed work and adds new scope as pending. `jg-plan` and `jg-challenge-plan` recommend it when the plan has parts that can each be finished and reviewed on their own, such as separate packages or repositories.
5. `jg-execute` builds the next milestone, runs its checks, and stops so you can run `jg-review` and `jg-push` yourself. `jg-review` checks the change against the plan and the milestone it belongs to, as well as the code. `jg-execute auto` builds every remaining milestone instead, reviewing and pushing each one before starting the next, then reviews the whole plan and follows jg-deliver for the approved delivery. After a supervised run's last milestone, run `jg-review` once more after `jg-push` for the same whole-plan review, then invoke jg-deliver. A named-milestone auto run keeps its unit limit and reports the remaining delivery. To check what a session delivered from the outside, run `jg-review-session` with that session's name from a separate session or another coding agent. If feedback remains, paste the complete report from its copyable code block into that session with `jg-feedback`; a clean result says `Nothing to forward.`

Both session skills give a short verdict and the scope checked when there is nothing to forward, including a brief resolution note on clean follow-ups. Findings, required decisions, and material verification gaps receive a copyable report introduced by `Forward this to <session> with jg-feedback:`. Its block contains only the assessment intended for the receiving agent; the destination line and your `Next step:` instructions stay outside it. You can explicitly request a full report for a clean result, which still says `Nothing to forward.`

A small, settled change, such as a few edits with nothing left to decide, skips steps 2 to 4: invoke `jg-execute` right after the discussion, and it builds the agreed task as one unit.

Use `jg-pause` at any point to stop the agent at a safe point and pick up later. Use `jg-debug` when something breaks and the cause isn't obvious. After diagnosis, it recommends a direct fix or planning with `jg-plan` and waits for your choice. Include 'diagnose and fix directly' upfront to skip that choice while keeping diagnosis and verification.
