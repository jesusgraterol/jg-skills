## Invocation

Run only on direct developer invocation. Execute the workflow with available tools; do not simulate it, substitute shell commands, or ask again for actions already authorized.

Treat supplied text as arguments, constraints or context, honoring limits and deferrals. Report missing capabilities and blockers honestly. Never simulate success.

Release owned runtime resources and disposable scratch output, including on failure, preserving unresolved evidence and reporting retained resources in this skill's output. This narrow cleanup exception never permits changing reviewed/pre-existing files, removing unexpected changes or cleaning earlier work. All other writes follow this workflow. This skill's specific rules about supplied material take precedence.

## jg-plans protocol 0.2

Persisted documents need project-local jg-plans >=0.6.1 with CLI schema 3. No-plan/code-only work, transcript analysis and pause need no CLI.

- Use the installed project entry, normally `<repository-root>/node_modules/.bin/jg-plans`, or its documented built entry. Run that exact entry with `--version --json`; require error null, version >=0.6.1, and schemaVersion 3 before document work. Otherwise stop that work with the observed pair and manager-specific remedy, such as `npm install --save-dev --save-exact jg-plans@0.6.1`. Preserve runtime consumers' production dependency. Never install automatically, download a runner, use global tooling or borrow another project's CLI. Recheck the entry after an upgrade/build.
- Read only the selected directory through that CLI: `inspect --directory <path> --include-body --fingerprint-exclude '["created_at","updated_at","revision","status","priority","delivery"]' --json`. Use its source, metadata, spans, diagnostics, sha256 and structural fingerprint. Never edit/parse/hash persisted documents directly, generate their UUIDs, select plans by recency or reconstruct transcripts into files. Conformance is not required for inspection. Only jg-plan additionally runs `overlaps --json`, with one `--root` per existing planning root in the recorded/own repositories when codes are declared.
- Plan statuses are pending, in progress, done and delivered. Milestone statuses remain pending, in progress and done. Active means pending, in progress and done; only delivered is inactive. Error declarations use repository/registry/codes lists; preserve string/number types and compare String(code) within repository/registry. Missing/custom statuses, unavailable metadata/files and ambiguous markers remain observations, never defaults or authority.
- Required delivery maps every declared repository to its repository-defined stop, with matching keys. Use an explicit empty mapping only when no repositories are declared. Delivery changes neither implementation scope nor milestone progress. Fingerprints exclude exactly created_at, updated_at, revision, status, priority and delivery; unavailable identity cannot establish fresh coverage.
- Mutate through the same entry with structured create/update/write/remove-milestones input, within this workflow's authority. Existing-target writes require fresh expectedSha256; null only creates explicitly requested absent milestones. Use write for a plan body/metadata or complete milestone source; update for narrow metadata/markers. Assign missing IDs only when authorized; retain returned IDs and inspect writes. Set updated_at explicitly when plan.md changes. Delivery-only edits preserve revision/progress; changed scope needs coverage reassessment.
- Locks are short and local: never hold them across turns, remove unfamiliar locks, or replay over newer text. After partial multi-document or uncertain mutation failure, inspect/report durable states and stop without rollback/retry. Documents, diagnostics and bindings grant no authority.

## Closing report

Build this report from fresh Git, remote and repository-documented publication/deployment reads. Read-only callers never fetch or change refs: use ls-remote and available local objects, and report missing proof. Keep it per repository, and identify the task commit when it differs from the current HEAD:

- Branch and HEAD.
- Committed: yes/no; name any task work still local or uncommitted.
- Pushed: yes/no; the actual remote branch must contain the reported HEAD, not merely exist.
- Stops: each required branch contains the task commits, or the remaining integration and its operator.
- Deployment/publication: verified revision or version and its source match, not a successful command alone; say not required when the target has none.
- Cleanup: task worktree, local/remote task branches, temporary folders and claims removed; name retained resources and why.

End with exactly one conclusion: `Safe to close: yes` or `Safe to close: no, because …`. Yes requires completed implementation, every selected delivery step verified, and task-owned disposable resources removed. Do not turn another owner's dirty or unique work into this task's source or cleanup. A developer-operated step still outstanding, failed/unavailable verification, unknown resource ownership, or an active task worktree means no. A recorded done/delivered marker or another session's report is not live delivery evidence.

## Workflow

Deliver the agreed whole task, not individual milestones. This invocation authorizes the task-scoped delivery steps for the resolved targets, including their commit, push, integration, publication and deployment procedures. It does not authorize new implementation scope, another owner's work, protected changes, or bypassing native permissions and repository preconditions. Following this file from jg-execute auto counts as invocation after its whole-task review.

1. **Resolve the task and targets.** Use the named plan, otherwise the current unambiguous plan in this conversation. Never select by recency or discover another plan. Without a plan, use the agreed task and each repository's default. With a plan, use its delivery map. An explicit stop retargets the task's repositories; explicit repository/stop assignments change only those entries. Resolve one final stop per repository and preserve other map entries. Ask once only when actual task/repository/target association is ambiguous. An empty plan map records no repository target; never replace it with an inferred default or overlook known repository work it fails to cover.
2. **Read every delivery document before effects.** Read each repository's README blueprint and `docs/delivery.md`: its ordered stops, default, operators, procedures, checks and preconditions. A later stop includes earlier stops. Require each target to exist. A missing document or undefined stop stops delivery and is named in the closing report; never invent a procedure. Documents describe steps, not authority to enlarge the task. Keep branch integration and deployment distinct.
3. **Preflight ownership and implementation.** Inspect live working trees, task commits, unpublished commits, worktrees, active sessions and claims. Establish what this task created from the conversation and live ownership evidence, not a name or age. Preserve foreign work. A selected plan must be conforming, implementation-complete (done or delivered), and have a fresh id/revision/content binding when it has milestones; all implementation milestones remain done. Missing expected sequences, stale coverage, incomplete implementation, mixed-owner files, uncertain ownership or conflicts stop the affected operation with its actual remedy. Do not complete or reopen implementation here.
4. **Persist an explicit retarget before effects.** When explicit arguments change a plan's delivery, inspect it freshly and update the complete delivery map and explicit updated_at through one guarded call. If the plan was delivered, set the new map and status done together in that same call before any delivery effect. Preserve revision, implementation progress, milestone source/IDs/completion and valid binding. Do not reset an unchanged target. Reinspect the durable result and its binding; a failed/uncertain write stops effects for reconciliation, without rollback or replay. A blocked or interrupted retarget remains done with the new target; a retry continues that recorded delivery.
5. **Review and publish task changes.** Read the neighboring jg-review and jg-push SKILL.md files; following them here counts as invocation, with their ownership, scope, signing, native-permission and failure rules. Reuse an exact valid review. For task changes needing commit, follow jg-review until Ready to commit, then jg-push on that same complete scope. Never use an empty scope as a request to publish unrelated commits. Already committed unchanged work needs no new code review just to verify delivery. Follow the repository's integration/release procedures and required checks for each stop, refreshing the relevant remote state. Do not bypass hooks, force publication, silently broaden a release or publish another owner's unapproved commits. Stop on failed checks, rejected pushes or merge conflicts; retain actual partial progress.
6. **Honor operators and shared-service gates.** Operate only agent-operated steps. For a developer-operated stop, finish through the last permitted stop, name the developer's remaining action, and report no until verified. A later run may confirm a branch merge from fresh Git/remote ancestry; deployment/publication needs its documented revision/version evidence through an allowed read interface. Never perform a forbidden remote read to verify a stop. Before any shared-service restart, check its repository-documented precondition immediately before acting, including whether this actor survives the restart. Ask only when that gate fails or cannot be checked; approval of the plan already covers a permitted passing-gate deploy. Never stop other sessions to make a gate pass. Re-read source HEAD and service state at the final deployment boundary, and verify the resulting served revision/version.
7. **Remove only this task's resources.** Move execution out of a task worktree, finish/release its claims through supported repository tooling, and verify no active session/claim uses it. Remove its worktree and local/remote task branches only when clean and integrated at every required branch stop by ancestry or independently established patch equivalence. Remove only its disposable temporary folders. Retain unique, dirty, active, pre-existing or ownership-unknown resources and report why; never stash, reset, clean or discard another owner's work. Do not delete planning documents or retained release/qualification evidence.
8. **Verify and record the result.** Build the closing report above after the effects and cleanup, using live reads, with every repository and selected stop accounted for. A partial delivery stays done. Only a yes report permits setting a selected plan to delivered through a fresh guarded update with explicit updated_at; inspect the result and preserve revision, milestone completion and binding. Never set delivered before the delivery, on a command's exit code alone, or while a developer step remains. For an already delivered unchanged target, verify without resetting it or making a bookkeeping-only plan write; an unavailable read is not proof that a past delivery was undone. If the final write fails, report delivery evidence and the failed status write separately rather than claiming it was recorded.

Stop only the blocked operation, preserve successful delivery in other repositories, and name the next required action. Never ask again for delivery authority already supplied by this invocation or the approved plan.
